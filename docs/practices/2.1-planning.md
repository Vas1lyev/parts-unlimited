# Практическая работа 2.1 — Гибкое планирование

## Результат

В GitHub подготовлен тестовый набор рабочих элементов Parts Unlimited и
настроен проект для гибкого планирования. GitHub Issues и GitHub Projects
используются как функциональный аналог Azure Boards из исходного задания.

## Подготовка тестовых данных

Обязательная подготовительная работа 2.0 выполнена без отдельного отчёта. Вместо
Azure DevOps Demo Generator тестовые данные созданы непосредственно в GitHub:

- эпик «Обучение продуктам»;
- функциональность «Осваиваем дашборды»;
- три элемента бэклога продукта в формате пользовательских историй;
- две технические задачи для первой пользовательской истории.

Иерархия рабочих элементов:

```text
Обучение продуктам
└── Осваиваем дашборды
    ├── Как клиент, я хочу просматривать новые учебные материалы
    │   ├── Добавить страницу для самых последних учебных материалов
    │   └── Оптимизировать запрос к данным последних учебных материалов
    ├── Как клиент, я хочу видеть недавно просмотренные учебные материалы
    └── Как клиент, я хочу запрашивать новые учебные материалы
```

## Настройка проекта

В GitHub Project созданы поля:

- `Команда`: `PUL-Web`, `External integrations`;
- `Область`: `Parts Unlimited`, `PUL-Web`, `External integrations`;
- `Тип работы`: `Эпик`, `Функциональность`, `Элемент бэклога`, `Задача`;
- `Деятельность`: `Разработка`, `Проектирование`, `Тестирование`,
  `Документирование`;
- `Трудоёмкость, ч` — числовая оценка задачи;
- `Осталось, ч` — оставшаяся работа;
- `Итерация`: `Итерация 1`, `Итерация 2`, `Итерация 3`.

Для планирования состояния используются русские статусы: `Новый`,
`Утверждено`, `Разработка завершена`, `Готово`.

## Планирование спринта

Рабочие элементы относятся к команде `PUL-Web`. Тестовая работа планируется на
`Итерацию 2`. Для двух технических задач заданы оценки:

| Задача | Деятельность | Трудоёмкость | Осталось |
| --- | --- | ---: | ---: |
| Добавить страницу для самых последних учебных материалов | Разработка | 5 ч | 8 ч |
| Оптимизировать запрос к данным последних учебных материалов | Проектирование | 3 ч | 3 ч |

Для воспроизведения сценария управления мощностью создан приватный ресурсный
элемент `Ресурс: Vas1lyev — Итерация 2`. В нём зафиксированы доступность
`1 ч/день`, отпуск продолжительностью `5` рабочих дней и доступная мощность
`8 часов`. Увеличение остатка первой задачи до 8 часов демонстрирует перегрузку:
вместе со второй задачей требуется 11 часов.

## Соответствие исходному заданию

- Azure DevOps Organization и Team Project заменены репозиторием и GitHub
  Project.
- Area Path и Team заменены полями `Область` и `Команда`.
- Iteration Path заменён встроенным полем итераций GitHub Project.
- Work Item Types заменены иерархией подзадач и полем `Тип работы`.
- Boards и Backlogs заменены табличными и канбан-представлениями проекта.
- Оценка и остаток работы хранятся в числовых полях проекта.

Настроены три представления проекта:

- `Бэклог` — полная иерархия рабочих элементов в табличном виде;
- `PUL-Web` — канбан-доска, отфильтрованная по команде;
- `Итерация 2` — канбан-доска работ выбранной итерации.
- `По исполнителям` — канбан-доска со строками по назначенным сотрудникам.

GitHub Projects не предоставляет полноценный учёт персональной доступности,
выходных дней и почасовой загрузки, описанный в Azure Boards. Поэтому для этой
работы значения сохранены в полях приватного ресурсного элемента, а полноценная
ресурсная диаграмма будет построена в GanttPRO на этапе календарного планирования.
